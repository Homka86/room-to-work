**План реализации «Есть место» — хакатон на 4 дня**

Команда: 4 человека, из них 2 разработчика. План подготовлен 5 сентября 2026 года.

В проверенной ветке `main` репозитория пока только README, прикладного кода нет. Исходные требования: каталог коворкингов, свободные места, выбор даты и часового слота, создание, просмотр и отмена своих броней, защита от двойного бронирования. Данные демонстрационные; при ошибке загрузки доступности бронирование отключается. Основание: [README на момент анализа](https://github.com/Homka86/room-to-work/blob/a0e4a5e816c7dc64e6417170c80009237f8defd6/README.md).

Цель четырёх дней: работающий по ссылке прототип, в котором два пользователя могут независимо пройти сценарий «найти место → забронировать → увидеть свою бронь → отменить», а одно место нельзя занять дважды на один час.

Ниже — предлагаемые решения для планирования, а не уже реализованные функции. Оценка предполагает знакомство разработчиков с JavaScript/TypeScript: примерно 48–56 часов разработки на двоих за четыре дня, включая 8–12 часов на исправления и интеграцию. Если стек команде незнаком, выбрать знакомый в первые два часа и сохранить те же границы MVP и контрольные точки.

**1. Объём MVP.**

Обязательно реализовать:

- Каталог из трёх тестовых коворкингов: название, адрес, часы работы, краткое описание.
- Страницу площадки с выбором даты, часового слота и рабочего места. Для демо достаточно 8–12 мест на площадку.
- Понятные состояния мест: свободно, занято, выбрано. Номер и текстовый статус должны дополнять цвет.
- Простой вход, подтверждение брони и раздел «Мои бронирования» с отменой.
- Сохранение данных в общей базе, серверную проверку правил и запрет двойной брони.
- Состояния загрузки, отсутствия свободных мест, конфликта и недоступности сервиса.
- Удобный основной сценарий на телефоне и ноутбуке.

Предлагаемые упрощения: один демогород; часовой пояс задан у площадки; одна бронь занимает одно место на один полный час; бронирование только будущих слотов в пределах следующих 14 дней; отмена доступна до начала слота. Правило «одному пользователю максимум одно место на один час» README не задаёт — дополнительное ограничение в этот план не включено.

Для показа подготовить два отдельных аккаунта Supabase Auth и форму входа. Самостоятельную регистрацию, восстановление пароля и социальный вход перенести за пределы хакатона. Это осознанное ограничение демо: проверять личные бронирования смогут пользователи подготовленных аккаунтов. Каталог доступен без входа; после входа сохраняется выбранное место и время.

Оплата и интеграции с реальными площадками уже исключены README. Также отложить карту, отзывы, чат, уведомления, кабинет владельца, визуальный редактор зала, брони на произвольные интервалы и автоматическую синхронизацию в реальном времени. Сетка пронумерованных мест достаточна для первого показа.

**2. Стек и устройство приложения.**

Рекомендация: Next.js + TypeScript для интерфейса и серверных обработчиков, Tailwind CSS для оформления, Supabase PostgreSQL для данных и Supabase Auth для входа. Next.js позволяет разместить HTTP-обработчики в том же приложении; для серверных сессий Supabase предусмотрена интеграция с cookies. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers), [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs).

Поток данных: браузер → серверные обработчики Next.js → PostgreSQL. Сервер проверяет сессию и бизнес-правила перед изменением брони. Все пользователи работают с общей базой; локальные заглушки нужны только для параллельной разработки интерфейса в первый день.

Для демо предлагается Vercel; поддержку выбранной среды, доступ команды и соединение с Supabase проверить в первый день. [Развёртывание Next.js на Vercel](https://vercel.com/docs/frameworks/full-stack/nextjs).

Минимальные проверки в CI: проверка типов, линтер, сборка и интеграционные тесты бронирования. SQL-миграции и наполнение демоданными хранить в репозитории. Зафиксировать версии зависимостей, добавить `.env.example` с названиями переменных и инструкцию запуска.

**3. Распределение команды.**

Роли двух участников без разработки — предложение; конкретные обязанности можно распределить по их навыкам.

| Участник | Зона ответственности | Измеримый результат |
|---|---|---|
| Разработчик 1 | Интерфейс, навигация, форма входа, подключение API | Полный пользовательский сценарий в браузере |
| Разработчик 2 | База, сессии, API, правила бронирования, деплой | Сохраняющиеся брони и корректная работа при конкуренции |
| Участник 3 | Пользовательский сценарий, макеты, тексты, демоданные | Четыре основных экрана и проверка понятности на 3–5 людях |
| Участник 4 | Ручная приёмка, список ошибок, презентация и репетиция | Пройденный чек-лист, сценарий защиты и резервное видео |

Оба разработчика согласуют формат API в начале первого дня и интегрируют изменения ежедневно. Утром — 15 минут на приоритеты; в конце дня — совместный проход сценария по общей ссылке. Блокер поднимать сразу, если он мешает работе дольше 30–45 минут.

**4. План по дням.**

| День | Разработчик 1 | Разработчик 2 | Остальная команда | Контрольная точка |
|---|---|---|---|---|
| 1 — основа | Каркас приложения; каталог; выбор даты, слота и места; форма входа | Схема и миграции; демоданные; два аккаунта; API каталога/доступности; первый деплой | Уточнить правила; набросать экраны; подготовить данные и чек-лист | По общей ссылке работает вход и отображается доступность из базы хотя бы для одной площадки |
| 2 — бронирование | Подтверждение; «Мои бронирования»; отмена; подключение серверных ошибок | Создание и отмена; проверка владельца; уникальный индекс; тест параллельных запросов | Проверять сборки двумя аккаунтами; уточнить тексты; собрать первые замечания | Полностью работает «выбрать → забронировать → увидеть → отменить»; после перезагрузки данные сохранены |
| 3 — надёжность | Мобильная версия; загрузка/ошибки/пустые состояния; обновление доступности; исправления | Тесты гонок, доступа и времени; повторные запросы; проверка развёрнутой версии | Проверка на 3–5 людях; повторная приёмка; слайды и сценарий демо | Все обязательные проверки ниже пройдены; новых функций больше не добавляем |
| 4 — показ | Исправить критические UX-ошибки; финальный проход на телефоне и ноутбуке | Финальная сборка; актуальные демоданные; README; проверка запуска и восстановления демосреды | Две репетиции; запись резервного видео; подготовка ответов жюри | Стабильная ссылка, два рабочих аккаунта, воспроизводимое демо, понятная инструкция запуска |

Первые два часа первого дня: зафиксировать стек, правила времени, роли, формат API и макеты основных экранов. Не ждать детального дизайна, чтобы начать базу и сервер.

Зависимости: правила → схема и контракт API → чтение доступности → запись брони → отмена → приёмка → финальное демо. Интерфейс первого дня и подготовка презентации выполняются параллельно. Развёртывание начать сразу, чтобы ограничения хостинга обнаружились до финального дня.

Последние 3–4 часа четвёртого дня оставить на репетицию и проверку демонстрационного окружения. Изменения в этот период — только для ошибок, мешающих основному сценарию.

**5. Данные и ключевые правила.**

| Сущность | Минимальные данные |
|---|---|
| `coworkings` | ID, название, адрес, описание, часовой пояс, фиксированное расписание |
| `seats` | ID, ID площадки, номер места, признак активности |
| `slots` | ID, ID площадки, время начала и конца |
| `bookings` | ID, ID пользователя Auth, ID площадки, ID места, ID слота, статус `active/cancelled`, время создания/отмены |

Пользователей хранит Supabase Auth; отдельная таблица профилей для этого демо не требуется.

Временные интервалы заранее создаются скриптом для демопериода. В базе используются абсолютные моменты времени (`timestamptz`), в интерфейсе — часовой пояс площадки. Скрипт создаёт только непересекающиеся полные часы внутри рабочего расписания. Обеспечить уникальность `(coworking_id, starts_at)` и длительность ровно один час; редактирование слотов пользователями не предоставлять. При развёртывании и подготовке показа скрипт дополняет сетку на 14 дней вперёд; повторный запуск не создаёт дубликаты и не меняет существующие брони. Для хакатона достаточно ручного запуска без фоновой задачи.

Место и слот обязаны принадлежать одной площадке. Закрепить это составными внешними ключами через `coworking_id`; соответствующие пары `(id, coworking_id)` в таблицах мест и слотов должны быть уникальны.

Для брони создать частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX bookings_one_active_per_seat_slot
ON bookings (seat_id, slot_id)
WHERE status = 'active';
```

Индекс запрещает две активные брони одного места и слота, сохраняя историю отмен. Такая условная уникальность поддерживается PostgreSQL. [Документация о частичных индексах](https://www.postgresql.org/docs/current/indexes-partial.html).

Проверка доступности перед сохранением помогает интерфейсу, но окончательное решение принимает база при вставке. При конфликте API возвращает `409`, интерфейс объясняет «Это место только что забронировали» и загружает актуальные места. Успех показывается после подтверждения сохранения сервером.

Отмена меняет статус конкретной записи, а повторное бронирование создаёт новую. Повторная отмена старой записи не должна затронуть новую бронь того же места. Историю можно определять по окончанию слота без отдельной фоновой задачи.

Сервер получает `user_id` из проверенной сессии, проверяет существование и активность места, принадлежность площадке, будущее время и допустимый горизонт. Чужие брони нельзя просматривать или отменять через подмену ID.

При предлагаемой серверной схеме включить RLS и закрыть прямой доступ клиентских ролей к прикладным таблицам; серверный ключ хранить только на сервере. Поскольку привилегированный ключ обходит RLS, фильтрация по текущему пользователю обязательна в обработчиках личных броней. [Supabase: RLS и права доступа](https://supabase.com/docs/guides/database/postgres/row-level-security).

Общая доступность вычисляется по активным броням всех пользователей. В ответ отдавать только сведения о местах и их занятости. Нельзя вычислять доступность по выборке «мои брони»: чужие занятые места тогда ошибочно окажутся свободными.

**6. Минимальный контракт API.**

| Запрос | Назначение |
|---|---|
| `GET /api/coworkings` | Каталог |
| `GET /api/coworkings/:id/slots?date=YYYY-MM-DD` | Разрешённые слоты на дату площадки |
| `GET /api/coworkings/:id/availability?slotId=...` | Места и занятость на выбранный слот |
| `POST /api/bookings` с `seatId`, `slotId` | Создать бронь текущего пользователя |
| `GET /api/bookings/me` | Свои брони с площадкой, местом, датой и статусом |
| `POST /api/bookings/:id/cancel` | Отменить свою будущую бронь |

В начале разработки согласовать формы ответов и ошибок: `400` — некорректные параметры, `401` — нужен вход, `404` — объект отсутствует или недоступен пользователю, `409` — место уже занято, `503` — данные временно недоступны.

Доступность загружать заново при смене даты/слота, после создания и отмены, а также после конфликта. Не использовать долгий кэш. Старый ответ на предыдущий выбор даты не должен перезаписывать новый экран. Если загрузка не удалась, показывать ошибку с повтором и блокировать подтверждение брони до успешного обновления.

Если ответ на создание потерялся после отправки, сначала перечитать свои брони: запись могла сохраниться. Двойное нажатие блокируется в интерфейсе, а повторный HTTP-запрос всё равно контролируется уникальным индексом.

**7. Критерии приёмки.**

Участник 4 ведёт результаты проверок. Разработчики автоматизируют критические проверки записи, доступа и времени на тестовой PostgreSQL; одни моки не доказывают защиту от гонок.

- [ ] Каталог, даты и места получаются из общей базы и корректно отображаются на телефоне.
- [ ] Два демо-аккаунта входят независимо; без сессии нельзя создать или отменить бронь.
- [ ] Созданная бронь появляется в личном разделе и сохраняется после перезагрузки.
- [ ] Одновременные запросы двух аккаунтов на одно место/слот дают ровно одну активную бронь; проигравший получает понятный конфликт.
- [ ] Двойной клик и повтор запроса не создают дубликат.
- [ ] Чужая бронь недоступна для просмотра и отмены, в том числе при прямом запросе к API.
- [ ] Прошедшее время, неактивное место и сочетание места/слота от разных площадок отклоняются сервером.
- [ ] Отмена освобождает место; другой пользователь может его занять; повтор старой отмены не удаляет новую бронь.
- [ ] Отменить активную бронь после начала её слота нельзя, в том числе прямым запросом к API.
- [ ] При сбое загрузки доступности видна ошибка, бронирование отключено; после восстановления данные запрашиваются заново.
- [ ] При смене даты и на границе суток показано время площадки; доступность не относится к предыдущему выбору.
- [ ] Пустой список мест и отсутствие личных броней имеют понятные сообщения.
- [ ] На финальной сборке проходят проверки типов, сборка и критические тесты; README позволяет второму разработчику воспроизвести запуск.

**8. Приоритеты при нехватке времени.**

Если к концу первого дня база не подключена по общей ссылке, разработчики совместно устраняют этот блокер в начале второго дня. Если к концу второго дня не проходит полный сценарий, третий день начинается с его завершения; до этого оформление не расширяется.

Сначала сокращать фильтры, фотографии, анимации и декоративную схему мест; число демоплощадок можно уменьшить. Сохранение в базе, проверку владельца, защиту от двойной брони, отмену и обработку ошибки доступности сохранять обязательными: это ядро требований README.

Для показа подготовить резервное видео рабочего сценария на случай проблем с интернетом. Тестовые данные создавать воспроизводимым скриптом; сброс выполнять только в выделенной демосреде и заранее, чтобы не удалять чужие данные во время проверки.

**9. Сценарий защиты и комплект сдачи.**

Рабочая версия выступления на 3–5 минут, с уточнением под регламент хакатона: коротко описать ситуацию студента между парами; выбрать место на будущий час; подтвердить и показать личную бронь; во втором браузере показать занятость того же места; отменить в первом и забронировать во втором. Параллельный конфликт дополнительно подтвердить тестом или короткой записью.

К сдаче должны быть готовы ссылка на приложение, репозиторий с инструкцией запуска и миграциями, тестовые аккаунты, список известных ограничений, короткая презентация и резервная запись. В интерфейсе обозначить демонстрационные данные и подтверждение брони внутри прототипа, как предусмотрено README.

После хакатона приоритеты: проверить сценарий с реальными студентами и одной площадкой; добавить полноценную регистрацию и кабинет владельца; затем оценить интеграции, уведомления и оплату по результатам пилота.
