# «Есть место» — краткая техническая инструкция

## Цель

За 4 дня сделать веб-MVP для поиска и бронирования рабочего места в коворкинге.

Пользователь должен уметь:

1. Открыть каталог коворкингов.
2. Выбрать площадку, дату, час и место.
3. Войти и создать бронь.
4. Посмотреть и отменить свою бронь.
5. Получить ошибку, если место уже занято или доступность не загрузилась.

## Стек

- Frontend/backend: Next.js + TypeScript.
- UI: Tailwind CSS.
- База и авторизация: Supabase PostgreSQL + Supabase Auth.
- Деплой: Vercel.
- Репозиторий: GitHub, ветки `main` и короткие feature-ветки.

Если команда уже уверенно работает с другим стеком, меняется только технология; структура данных и API остаются такими же.

## Архитектура

`Браузер → Next.js API → Supabase`.

Браузер не записывает данные напрямую. Сервер проверяет сессию пользователя, параметры брони и права доступа.

## Минимальная база данных

```text
coworkings
  id, name, address, description, timezone

seats
  id, coworking_id, name, is_active

slots
  id, coworking_id, starts_at, ends_at

bookings
  id, user_id, coworking_id, seat_id, slot_id,
  status(active/cancelled), created_at, cancelled_at
```

Слоты — фиксированные часовые интервалы на ближайшие 14 дней. Место и слот должны относиться к одному коворкингу.

Обязательное ограничение PostgreSQL:

```sql
CREATE UNIQUE INDEX one_active_booking
ON bookings (seat_id, slot_id)
WHERE status = 'active';
```

Проверка доступности перед вставкой нужна для интерфейса, но окончательное решение принимает этот индекс. При конфликте API возвращает `409`.

## API

```text
GET  /api/coworkings
GET  /api/coworkings/:id/slots?date=YYYY-MM-DD
GET  /api/coworkings/:id/availability?slotId=...
POST /api/bookings              { seatId, slotId }
GET  /api/bookings/me
POST /api/bookings/:id/cancel
```

Правила:

- `401` — пользователь не вошёл;
- `400` — неверные параметры;
- `409` — место уже занято;
- `404` — объект не найден или не принадлежит пользователю;
- `503` — доступность временно не загрузилась.

`user_id` брать из серверной сессии, а не из тела запроса. Отмена разрешена только владельцу будущей активной брони. Отмена меняет статус на `cancelled`, удалять запись нельзя.

## План на 4 дня

### День 1 — каркас

- Создать Next.js-проект и подключить Supabase.
- Создать миграции, демоданные и два тестовых аккаунта.
- Реализовать каталог, выбор даты и слота.
- Развернуть первую версию.

**Результат:** площадка открывается по ссылке, слоты и места приходят из базы.

### День 2 — бронирование

- Реализовать API создания и отмены.
- Подключить форму входа.
- Добавить страницу «Мои бронирования».
- Подключить уникальный индекс и обработку `409`.

**Результат:** работает сценарий «выбрать → забронировать → увидеть → отменить».

### День 3 — проверка

- Проверить два одновременных запроса на одно место.
- Проверить запрет доступа к чужим броням.
- Добавить состояния загрузки, ошибки и отсутствия мест.
- Адаптировать основной экран под телефон.

**Результат:** критические ошибки исправлены, новые функции не добавляются.

### День 4 — сдача

- Заполнить будущие слоты на 14 дней.
- Проверить production-сборку и инструкцию запуска.
- Провести финальную приёмку двумя аккаунтами.
- Подготовить презентацию и резервную видеозапись.

**Результат:** стабильная ссылка, рабочие аккаунты и воспроизводимый запуск.

## Распределение команды

- Разработчик 1: интерфейс и подключение API.
- Разработчик 2: база, авторизация, API, деплой.
- Участник 3: макеты, тексты, демоданные, UX-проверка.
- Участник 4: тестирование, список ошибок, презентация и репетиция.

## MVP готов, если

- бронирование сохраняется после перезагрузки;
- два пользователя не могут занять одно место на один час;
- отмена освобождает место;
- чужую бронь нельзя посмотреть или отменить;
- при ошибке доступности кнопка бронирования отключена;
- проходят `typecheck`, `lint`, `build` и тест основного сценария.

Не включать в эти 4 дня: оплату, карту, отзывы, уведомления, кабинет владельца, реальные интеграции и произвольные интервалы времени.
